# Компилятор, проекты и бэкенды

## Команды

```
orbitron run [файл.ot] [опции]     собрать и запустить
orbitron build [файл.ot] [опции]   собрать исполняемый файл
orbitron check [файл.ot]           только проверить код
orbitron fmt [--check] [файлы...]  отформатировать исходники
orbitron new <имя>                 создать проект
orbitron <файл.ot> [опции]         то же, что build
```

Если файл не указан, `run`, `build` и `check` ищут `orbitron.toml` в текущем каталоге и выше.

| Опция | Значение |
|---|---|
| `-o <путь>` | путь к результату (по умолчанию: имя файла без `.ot`; для JVM добавляется `.jar`) |
| `--backend llvm\|jvm` | выбор бэкенда (по умолчанию `llvm`) |
| `--emit` | сохранить сгенерированный `.ll` или `.java` вместо сборки |
| `-O0` … `-O3` | уровень оптимизации clang (по умолчанию `-O2`) |
| `--keep-temps` | не удалять промежуточные файлы |
| `-v` | показать этапы сборки и вызываемые команды |

Переменные окружения:

- `ORBITRON_HOME` — каталог, внутри которого лежит `stdlib/`;
- `ORBITRON_CC` — компилятор C/LLVM IR вместо `clang`.

## Проекты

`orbitron new app` создаёт:

```
app/
├── orbitron.toml
├── .gitignore
└── src/
    └── main.ot
```

```toml
[project]
name = "app"
version = "0.1.0"

[build]
main = "src/main.ot"     # точка входа (по умолчанию)
output = "build/app"     # результат (по умолчанию build/<name>)
backend = "llvm"         # или "jvm"
```

В проекте модули подключаются относительно импортирующего файла: `import "parser";` подключит `src/parser.ot` из `src/main.ot`.

## Форматтер

`orbitron fmt` приводит код к единому стилю: отступ 4 пробела, `{` на той же строке, пробелы вокруг бинарных операторов, одна пустая строка между объявлениями. Комментарии, пустые строки между инструкциями и исходная запись чисел (`0xff`, `1_000`) сохраняются. Однострочные блоки из одной инструкции остаются однострочными.

- `orbitron fmt` перезаписывает все `.ot` проекта или текущего каталога;
- `orbitron fmt --check` ничего не меняет и возвращает код 1, если файлы нужно отформатировать (удобно в CI);
- `orbitron fmt --stdout file.ot` выводит результат в stdout.

## Бэкенд LLVM

Компилятор генерирует текстовый LLVM IR и передаёт его `clang` вместе с небольшим рантаймом на C ([`runtime/orbitron_rt.c`](../runtime/orbitron_rt.c), встроен в компилятор). Получается обычный нативный исполняемый файл без зависимостей, кроме libc и libm.

Особенности:

- поддерживает `extern fn`;
- динамически созданная память не освобождается до завершения процесса;
- посмотреть IR: `orbitron build file.ot --emit` создаёт `file.ll`.

## Бэкенд JVM

Компилятор генерирует `Main.java`, компилирует его `javac` вместе с рантаймом [`runtime/OtRt.java`](../runtime/OtRt.java) и упаковывает в исполняемый `.jar`:

```bash
orbitron build app.ot --backend jvm     # → app.jar
java -jar app.jar
```

Особенности:

- нужен JDK 17 или новее;
- `extern fn` не поддерживается;
- программа выполняется в потоке со стеком 1 ГБ, поэтому глубокая рекурсия работает так же, как в нативной сборке;
- полученный jar можно превратить в нативный файл через GraalVM: `native-image -jar app.jar`.

## Совместимость бэкендов

Набор сквозных тестов (`cargo test`) собирает каждую программу из `tests/programs` обоими бэкендами и требует побайтово одинакового вывода и кода завершения. Одинаковыми гарантированно получаются:

- целочисленная арифметика, включая переполнение, деление `int::MIN / -1` и сдвиги;
- форматирование `float`;
- приведение `float → int` с насыщением;
- строковые операции в байтах UTF-8;
- порядок вычисления (слева направо);
- тексты ошибок выполнения и код завершения 101.
